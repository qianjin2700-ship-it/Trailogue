# TRAILOGUE V2 — 产品规格（Product Spec）

> 阶段：Phase A（定位与范围，不含实现排期细节）
> 状态：待评审

---

## 1. 一句话定位

**Trailogue 把一次旅行的照片与片段，变成一篇读得进去的图文故事，以及一本拿得出手的旅行杂志。**

英文口径：*AI-powered travel memory storytelling.*

不是「相册工具」，不是「AI 写作工具」，也不是「电子手帐」。它的价值在于**把散落的照片变成有叙事的成品**，并且这个成品值得保存、可以分享、能打印。

---

## 2. 核心路径（唯一主链）

```
Trip  →  Photos & Memories  →  Story  →  Magazine  →  Share / Export
```

这是 2.0 的**唯一主链**。任何功能如果不能落在这条链上，就不进 2.0。

| 环节 | 用户动作 | 系统产出 |
|---|---|---|
| Trip | 起个旅行名、选日期、填目的地 | 一个容器 |
| Photos & Memories | 选照片、加备注/地点 | 有序的照片集 + 上下文 |
| Story | 点生成、读、改文字 | 图文叙事页 |
| Magazine | 切到 Magazine | 画册成品 |
| Share / Export | 分享链接 / 导出 PDF | 可传播的产物 |

**判定标准（沿用 1.0 的口径）**：是否阻塞新用户走完这条主链。是则必修，否则记录。

---

## 3. 两种成品形态（且只有两种）

### 3.1 Story —— 以阅读为核心

- 本质：**一篇文章，照片穿插其中**。
- 阅读体验优先：字号、行高、段距、章节节奏都为「连续阅读」服务。
- 照片是叙事的**佐证**，不是主角；一张照片可以很小，也可以通栏，但整体视觉克制。
- 强调**时间顺序**与**故事连续性**（第一章到最后一章要读得下去）。
- 可编辑、可版本化、可对比。
- 分享出去 = 一个手机上好读的网页。

**Story 的反面**（不要做）：
- 不做封面大图 + 一堆小图拼贴（那是 Magazine）；
- 不做模板选择器（用户只看到一种 Story）；
- 不做花哨动效。

### 3.2 Magazine —— 以视觉成品感为核心

- 本质：**一本旅行杂志**，有封面、有页面节奏、有大图、有引语。
- 视觉优先：图片构图、跨页关系、页码、章节分隔、引语块。
- 适合收藏、分享、打印成 PDF。
- 是 2.0 的**核心视觉卖点**——用户第一眼「哇」的应该是 Magazine。

**Magazine 的反面**（不要做）：
- 不做「让大模型决定每个元素放哪」的像素级 AI 排版（不可控、不稳定、无法测试）；
- 不做多主题商城（2.0 只保留一套高完成度版式，Pro 再加主题）。

### 3.3 明确不恢复的旧形态

| 旧形态 | 状态 |
|---|---|
| Minimalist | ❌ 不恢复（代码保留为死代码，1.0 过审后清理） |
| Memoir | ❌ 不恢复 |
| List | ❌ 不恢复 |
| 其他多模板模式 | ❌ 不恢复 |

用户在产品里**只看到两个切换项**：`Story | Magazine`。

## 4. 用户与场景

### 4.1 主要用户

| 用户 | 特征 | 关心什么 |
|---|---|---|
| 记录型旅行者 | 一次旅行拍 200–800 张，回来从不整理 | 「能不能自动帮我理出来」 |
| 分享型用户 | 想发朋友圈/发给家人，但懒得写文案 | 「能不能一键变成能发的东西」 |
| 纪念型用户 | 想把一次重要旅行（蜜月、亲子、毕业）留存 | 「能不能做成一本能打印的书」 |

### 4.2 Jobs to be done

1. 旅行结束后，**把 300 张照片变成 3 分钟能读完的东西**。
2. 把成品**发给没同行的人看**，且对方不用装 App。
3. 三五年后**还能翻出来看**，最好能打印。

## 5. 2.0 范围

### 5.1 In scope（2.0 要做）

| 项 | 说明 |
|---|---|
| Story 组件系统 | 稳定的图文块体系（见 STORY_DESIGN） |
| Magazine 组件系统 | 固定版式组件 + 程序化排版引擎（见 MAGAZINE_DESIGN） |
| 版式引擎 | 基于照片真实宽高比 + 内容长度做确定性决策 |
| Book Preview 收口 | 消除重复入口、统一按钮语言、明确当前形态 |
| 分享一致性 | 所见即所得（已在 1.0 完成基础版，2.0 提升保真度） |
| PDF 质量 | 版式与 App 内 Magazine 一致 |
| Pro 架构预留 | 只留挂载点，不实现付费 |

### 5.2 Out of scope（2.0 不做）

- 视频、Live Photo、360 照片
- 多人协作 / 共享编辑
- 社交 feed、关注、点赞
- 地图轨迹、行程规划
- Web 端编辑器（只有只读分享页）
- Android
- 实时协作、离线编辑
- AI 对话式改稿

### 5.3 明确禁止（Phase A 内）

- 改生产数据库结构
- 改 `/v1` 行为
- 改 Apple 登录、账户删除
- 部署 Railway、触发 EAS production build

## 6. 体验原则

1. **成品优先于过程**。用户打开 App 最想看到的是「我的故事/我的杂志」，不是操作面板。
2. **克制**。留白、单一字体家族、少量强调色。视觉重量来自照片，不来自装饰。
3. **确定性**。同一份内容 + 同一批照片，任何时候渲染结果一致（版式引擎无随机、无时间依赖）。
4. **不假装智能**。AI 只做它擅长的（写文字、理解内容），排版交给程序。
5. **永不空手**。空状态、失败状态都要给出「下一步能做什么」，而不是一句报错。

## 7. 成功判据（2.0 上线后）

| 指标 | 目标 | 度量方式 |
|---|---|---|
| 主链完成率 | 建旅行 → 生成故事 ≥ 70% | 服务端事件计数 |
| Story 阅读完成 | 打开 Story 且滚动到底 ≥ 50% | 客户端埋点（需先补，见下） |
| Share 使用率 | 生成过故事的用户中 ≥ 30% 分享过 | `share_links` 表 |
| PDF 导出率 | ≥ 10% | 客户端事件 |
| 崩溃/白屏 | 0（Magazine 渲染不得出现空白页） | TestFlight / 用户反馈 |

> 注：1.0 **没有任何 analytics / telemetry**（已核实）。上述指标目前只能从数据库侧推断。是否引入匿名埋点是**独立决策**，不在 2.0 Phase A 范围内，也不应顺手加进包体。

## 8. 与 1.0 的关系

| 维度 | 1.0 | 2.0 |
|---|---|---|
| 商业模式 | $2.99 买断 | 暂不变（Pro 只预留） |
| 成品形态 | Story + Magazine（Magazine 仅一套版式） | Story + Magazine（两套都组件化） |
| 版式实现 | 4 处重复 HTML/CSS | 1 套文档模型 + 1 个渲染器 |
| 分享 | story / magazine 两种 view | 保真度提升，URL 契约不变 |
| 数据 | 现有 9 表 | Phase A 不改表；后续只加可选字段 |

**2.0 不是重写**：数据、API、登录、存储全部沿用 1.0。2.0 改的是**渲染层与产品表达**。
