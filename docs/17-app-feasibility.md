# 17. App 化可行性评估

> 整理日期：2026-08-31
> 评估对象：将「旅迹成书」小程序扩展为独立移动 App（Android / iOS）
> 数据口径：基于当前代码库实测统计，非估算

---

## 0. 结论摘要

**不建议在当前阶段开发 App。** 三个层面存在障碍，按严重性排序：

| 层面 | 结论 | 性质 |
|---|---|---|
| **合规** | AI 生成类目在国内安卓商店需算法备案 + 安全评估报告，个人主体实操极难 | **硬门槛，可能卡死** |
| **商业** | 产品 1/4 的前端代码服务于微信生态分享裂变，App 端无法替代 | **价值折损，不可逆** |
| **技术** | 云函数核心逻辑可复用，但鉴权层与前端需重写 | **工作量，可解决** |

**建议顺序**：等小程序审核结果 → 用真实数据验证需求 → 再评估 App。

小程序审核结果本身就是一次低成本的合规实测：如果微信对 AIGC 类目提出了你没预料到的要求，那么 App 端只会更严。

---

## 1. 合规：最大的硬门槛

### 1.1 关键发现：AI 生成服务在国内应用商店属于「需资质类目」

华为应用市场官方资质文档（developer.huawei.com/consumer/cn/doc/80301）将
**「深度合成或生成式人工智能服务」** 单列为一类需要资质证明的应用内容，要求四项：

1. **AI 生成合成内容标识材料**
   - 应用未提供生成内容导出/下载功能 → 提供应用内已添加内容**显式标识**截图
   - 应用提供导出/下载功能 → 提供《人工智能生成合成内容标识说明函》
     （本产品有长图/PDF 导出，属于后者）
2. **互联网信息服务算法备案**查询结果截图（beian.cac.gov.cn，备案类型：生成合成类）
3. **《安全评估报告》**
4. 安全评估报告在**全国互联网安全服务管理平台**的提交结果截图，
   且**现场检查结果为「通过」或审核状态为「审核通过」**

> ⚠️ 这是**应用商店的审核规则**，不是法律条文本身。平台规则通常严于法律。
> 提审前请以各商店当时的最新资质清单为准。

### 1.2 与法律规定的差异（重要，不要混淆）

《生成式人工智能服务管理暂行办法》第 17 条：

> 提供**具有舆论属性或者社会动员能力**的生成式人工智能服务的，应当按照国家有关规定
> 开展安全评估，并履行算法备案手续。

| 维度 | 法律规定 | 应用商店规则 |
|---|---|---|
| 触发条件 | 限「具有舆论属性或社会动员能力」 | 按功能类目一刀切，未见例外条款 |
| 本产品是否触发 | 个人旅行故事生成，大概率**不触发** | **触发** |

**结论**：法律层面你可能不触发第 17 条义务，但**商店审核看的是商店规则**。
个人旅行相册工具是否真的会被要求提交算法备案，存在解释空间，
但这意味着你要用一次提审周期（1~7 天，被拒则翻倍）去赌这个解释。

### 1.3 个人主体的现实约束

| 事项 | 个人主体 | 说明 |
|---|---|---|
| 安卓商店开发者账号 | ✅ 可注册（身份证 + 人脸识别，无年费） | 华为官方论坛确认个人可上架无资质门槛的纯工具类 |
| 软著 | ✅ 可办 | 1~3 个月，加急 1~5 工作日 |
| ICP 备案 | ✅ 可办（需域名 + 接入商） | 7~15 工作日 |
| 网信办 APP 备案 | ✅ 可办 | 仅限**非经营性**工具类 |
| **算法备案** | ⚠️ 未明确禁止，但实操困难 | 需说明算法机制机理、训练数据来源等 |
| **安全评估报告 + 现场检查** | ❌ 极难 | 需配合现场检查，个人主体基本无先例 |
| ICP 许可证（经营性） | ❌ 不可办 | 需 100 万注册资本，个人主体无资格 |

**注意 ICP 备案的隐藏成本**：备案需要域名和接入商。
当前小程序用的是云开发环境自带域名，没有独立域名。
做 App 需要先注册域名 + 走腾讯云接入商备案流程。

### 1.4 iOS 侧相对宽松，但年费与审核是另一道坎

- Apple Developer 个人账号：99 美元/年（约 700 元）
- 苹果对个人开发者友好，无软著强制要求
- 但：审核最严，「功能过于简单」会被以
  *Lacks sufficient lasting value* 为由拒绝
- 若未来做付费/会员：**必须走苹果 IAP**，苹果抽成 15~30%，
  且禁止引导到微信/支付宝支付

### 1.5 合规基础盘点：已做 / 缺失

| 项 | 状态 | 位置 |
|---|---|---|
| 导出物带「AI 生成」标识 | ✅ 已有 | `miniprogram/utils/album-export.ts:548` 页脚文案「由 旅迹成书 · AI 生成」 |
| 页面内浏览时的 AI 内容提示 | ❌ 缺失 | 故事预览/分享查看页无显式标识 |
| 分享海报的 AI 标识 | ❌ 缺失 | 小程序码海报未标注 |
| 用户协议（AI 服务条款） | ⚠️ 待核 | 《暂行办法》第 9 条要求与使用者签订服务协议 |
| 投诉举报入口 | ❌ 缺失 | 《暂行办法》第 15 条要求 |

> 上述缺失项**与是否做 App 无关，小程序端也应补齐**。
> 建议列入小程序通过审核后的第一批迭代。

## 2. 商业：获客路径会断裂

这是最容易被忽略、但影响最大的一层。

### 2.1 实测：1/4 的前端代码服务于微信生态传播

代码库统计（`miniprogram/` 下 `.ts` 文件）：

| 能力 | 引用处数 | App 端命运 |
|---|---|---|
| `scene`（分享场景值识别） | 28 | ❌ 完全失效 |
| 小程序码生成（`getwxacode`） | 8 | ❌ 失效，需改用普通二维码 |
| `onShareAppMessage` | 3 | ❌ 失效 |
| `showShareMenu` | 1 | ❌ 失效 |
| **小计** | **40 / 151 处 wx.* 调用 ≈ 26%** | |

### 2.2 为什么这无法替代

产品当前的核心增长路径是：

```
用户生成故事书 → 分享链接/海报到微信 → 好友点开即看（无需安装）→ 转化新用户
```

**「点开即看、无需安装」是小程序独有的转化优势。**

改成 App 后同样的路径变成：

```
用户生成故事书 → 分享链接到微信 → 好友点开 → 提示下载 App → 流失
```

行业经验：这一步的转化损耗通常在 90% 以上。
对一个还处于「验证有没有人愿意用」阶段的产品，这是致命的。

### 2.3 时点判断

| 事实 | 含义 |
|---|---|
| 小程序刚提审，尚未发布 | 0 真实用户，需求未经验证 |
| 尚未验证付费意愿 | 商业模式未跑通 |
| 核心功能仍在补（照片排序刚做完） | 产品完成度还在爬坡 |

在这个时点投入 App，等于**在产品市场契合（PMF）验证之前，
先承担一套全新的合规成本 + 一个重写的前端 + 一条断裂的获客路径**。

## 3. 技术：可复用与需重做的部分

### 3.1 实测数据

| 指标 | 数值 |
|---|---|
| 小程序端源码（.ts + .wxml + .wxss） | 7,807 行 / 39 个 TS 文件 / 12 个页面 |
| `wx.*` API 调用 | 151 处 |
| 其中 `wx.cloud.*` | 11 处 |
| 云函数 `cloud.getWXContext()` 调用点 | 11 处（10 个业务函数全覆盖） |
| `openid` 变量引用（云函数） | 178 处 |

### 3.2 关键架构约束：鉴权体系是微信绑定的

所有 10 个业务云函数都通过 `cloud.getWXContext()` 获取 openid 作为用户身份。
App 端通过 CloudBase 多端 SDK（JS SDK / Flutter SDK）调用时，
**不存在微信上下文，取不到 openid**。

腾讯云官方文档《打通小程序和移动应用 APP，实现一云多端》明确指出：
跨端打通用户体系时，**在 APP 端使用微信登录是必要条件**（依赖 unionid 关联）。

这意味着两个选项：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. App 端接微信登录** | 用户在 App 内用微信授权，后端用 unionid 关联小程序 openid | 需微信开放平台账号 + 应用审核（又一道审核）；178 处 openid 逻辑要改为 unionid 双轨 |
| **B. App 端独立用户体系** | 手机号/邮箱注册，与小程序数据不互通 | 云函数鉴权层重写；两套用户数据，运营割裂 |

两条路都要动 178 处引用。**这是本项目 App 化的核心技术债。**

### 3.3 好消息：云函数业务逻辑可复用

值得肯定的是，当前架构把核心资产放在了云函数：

| 资产 | 位置 | 是否可复用 |
|---|---|---|
| AI prompt 工程 | `internal-generateStory` | ✅ 完全复用 |
| 照片聚类与编排降级 | `internal-generateStory` | ✅ 完全复用 |
| EXIF 解析与逆地理 | `internal-processMeta` | ✅ 完全复用 |
| PDF 合成 | `export`（pdf-lib） | ✅ 完全复用 |
| 用量统计 / 埋点 | `usage.ts` / `common.ts` | ⚠️ 需适配鉴权 |

CloudBase 本身支持多端接入（`@cloudbase/js-sdk` + `@cloudbase/adapter-uni-app`、
`cloudbase_flutter` 等），**后端不需要重写**。

> 这条验证了之前的一个架构决策是对的：
> 核心逻辑放云端、前端只做壳，换端时损失可控。

### 3.4 前端框架选型（若决定做）

| 方案 | 复用率 | 代价 | 适配度 |
|---|---|---|---|
| **uni-app** | 需重写前端，业务逻辑可搬 | Vue 语法；`@cloudbase/adapter-uni-app` 官方支持 | ⭐⭐⭐⭐ 最贴合 CloudBase |
| **Taro** | 需重写前端 | React 语法；京东系，小程序侧成熟 | ⭐⭐⭐ |
| **Flutter** | Dart 全新 | `cloudbase_flutter` 可用但社区小 | ⭐⭐ 性能最好，成本最高 |
| **原生双端** | 0 | 两套代码 | ⭐ 不推荐 |

**诚实提醒**：不要指望「一套代码多端」。
多端框架的现实是复用 70~80% 的业务逻辑，
**UI 层和平台 API 层仍需分别适配**。
本项目以下部分基本要重做：

- 照片拖拽排序组件（`components/sortable-grid`，刚写完，基于小程序 touch 事件体系）
- Canvas 长图渲染（`utils/album-export.ts`，基于小程序 Canvas 2D API）
- 保存到相册 / 打开文档预览（平台 API 完全不同）
- 热更新（`wx.getUpdateManager` → 需自建或依赖商店更新）

### 3.5 App 端额外需要补的能力（小程序由平台代管）

| 能力 | 小程序 | App |
|---|---|---|
| 版本热更新 | 平台提供 | 需自建或走商店审核 |
| 支付 | 微信支付（个人主体受限） | 苹果 IAP 强制 + 安卓渠道 |
| 推送通知 | 模板消息（受限） | 需接厂商推送通道 |
| 崩溃监控 | 平台提供基础能力 | 需接第三方 SDK |
| 加固 | 平台打包 | 各商店强制要求加固 |

## 4. 触发条件：什么时候该做 App

把 App 化当作一个**有前置条件的决策**，而不是一个待办事项。
满足以下任一条件时重新评估：

| 触发条件 | 说明 |
|---|---|
| 小程序月活稳定 > 5,000 且增长依赖非微信渠道 | 说明需求已验证，且微信生态不再是唯一获客路径 |
| 用户主动反馈「想要 App」形成规模 | 真实需求信号，而非开发者的一厢情愿 |
| 需要小程序做不到的能力 | 如后台持续上传、系统级相册访问、桌面小组件 |
| 已注册公司主体 | 合规门槛大幅下降，算法备案/安全评估具备可行性 |
| 有明确的出海计划 | 海外市场 Google Play / App Store 是主渠道，国内合规不适用 |

**在此之前，App 化是负债不是资产。**

## 5. 决策记录

**时间**：2026-08-31
**背景**：小程序已提交审核，等待结果中；用户提出 App 化想法
**决定**：暂不启动 App 开发

**理由**：
1. 合规层面存在个人主体难以跨越的硬门槛（算法备案 + 安全评估现场检查）
2. 商业层面会切断当前唯一的、也是最适合本产品的获客路径
3. 技术层面虽可行（后端可复用），但鉴权重构与前端重写需要数月工作量
4. 产品尚未验证 PMF，此时投入 App 是过早优化

**保留动作**：
- 等小程序审核结果，作为合规环境的实测参考
- 补齐 AI 内容标识与用户协议（小程序端也要做，见 1.5）
- 若未来注册公司主体，本文档第 1 节需重新评估
